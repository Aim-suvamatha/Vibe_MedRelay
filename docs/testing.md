# testing.md — Checklist ทดสอบระบบ MedRelay

Checklist นี้แบ่งเป็น 3 ระดับ ใช้คนละเวลากัน

| ระดับ | ใช้เมื่อไร | เวลาที่ใช้ |
|---|---|---|
| **A. Pre-commit** | ทุกครั้งก่อน commit | 2 นาที |
| **B. Functional** | ก่อน deploy และก่อนส่งงาน 13 ก.ย. | 45 นาที |
| **C. UAT** | ทดสอบกับผู้ใช้จริง 3–5 คน | 30 นาที/คน |

---

## A. Pre-commit Checklist (2 นาที ทุกครั้ง)

### A1 — Secrets

- [ ] `git status` ไม่มีไฟล์ `.env`, `.env.local` (มีได้เฉพาะ `.env.example`)
- [ ] รันคำสั่งตรวจ secret แล้วผ่าน

```bash
git diff --cached | grep -nE 'eyJ[A-Za-z0-9_-]{10,}|sk-[A-Za-z0-9]{10,}|postgres://|service_role' \
  && echo "⚠️  พบ secret — หยุด commit" || echo "✅ ผ่าน"
```

- [ ] ไม่มี `service_role` ในไฟล์ที่มี `"use client"`

```bash
grep -rl '"use client"' src | xargs grep -l 'service_role' && echo "⚠️  พบ" || echo "✅ ผ่าน"
```

### A2 — ข้อมูล

- [ ] ไม่มีชื่อจริงของบุคคลใดใน seed / test / comment
- [ ] ไม่มีเลขบัตรประชาชน 13 หลักที่ไหนเลย

```bash
grep -rnE '[0-9]{13}' src supabase --include='*.ts' --include='*.tsx' --include='*.sql' \
  && echo "⚠️  ตรวจดูว่าใช่เลข 13 หลักหรือไม่" || echo "✅ ผ่าน"
```

### A3 — Build

- [ ] `npm run typecheck` ผ่าน
- [ ] `npm run lint` ผ่าน
- [ ] `npm run build` ผ่าน

## B. Functional Checklist (45 นาที ก่อน deploy)

### B1 — Security และ RLS (ทำก่อนเสมอ — ข้อนี้พังคือพังทั้งระบบ)

- [ ] ทุกตารางเปิด RLS — รันแล้วต้องไม่มีแถวไหนเป็น `false`

```sql
select tablename, rowsecurity from pg_tables
where schemaname = 'public' order by tablename;
```

- [ ] ทุกตารางมี policy อย่างน้อย 1 ข้อ

```sql
select t.tablename, count(p.policyname) as policies
from pg_tables t
left join pg_policies p on p.tablename = t.tablename and p.schemaname = 'public'
where t.schemaname = 'public'
group by t.tablename having count(p.policyname) = 0;
-- ต้องได้ 0 แถว
```

- [ ] **ทดสอบข้ามหน่วย** — login เป็นผู้ใช้หน่วย A แล้วเปิด `/track/<caseId ของหน่วย B ที่ไม่เกี่ยวข้อง>` → ต้องไม่เห็นข้อมูล
- [ ] **ทดสอบ escalation** — sender พยายาม `update profile set roles = '{admin}'` ของตัวเอง → ต้องถูกปฏิเสธ
- [ ] **ทดสอบ immutability** — พยายาม `delete from assessment` → ต้องถูกปฏิเสธ แม้เป็น admin
- [ ] `.env.local` ไม่อยู่ใน git history — `git log --all --full-history -- .env.local` ต้องว่าง
- [ ] เปิด DevTools → Network → ไม่พบ `service_role` key ใน response ใดๆ
- [ ] เปิด DevTools → Sources → ค้นหา `sk-` และ `service_role` ใน bundle → ไม่พบ

### B2 — Auth

- [ ] login ด้วยเลขทหาร 10 หลัก + OTP สำเร็จ
- [ ] กรอกเลขที่ไม่มีในระบบ → error message **เหมือนกรณีปกติ** (ไม่บอกว่าไม่พบเลขนี้)
- [ ] กรอกเลขไม่ครบ 10 หลัก → ถูก validate ก่อนส่ง request
- [ ] เข้า `/dispatch` โดยไม่ login → redirect ไปหน้า login
- [ ] logout แล้วกด back → ไม่เห็นข้อมูลเดิม
- [ ] ผู้ใช้ที่มี 2 บทบาท เห็น tab ครบทั้ง 2 บทบาท

### B3 — F1 หน้าขอส่งกลับ

- [ ] ส่งคำขอสำเร็จ → เกิด 3 แถว: `case` + `transfer_leg` (leg_no=1) + `assessment` (kind='initial')
- [ ] `requested_at` มีค่าโดยที่ไม่ได้กรอกเอง
- [ ] `case_code` รูปแบบ `MR-2569-XXXX` และไม่ซ้ำ
- [ ] `is_synthetic = true` ทุกแถว
- [ ] ส่งฟอร์มว่าง → ถูก validate ไม่ให้ส่ง
- [ ] **ทดสอบ transaction** — ปิดเน็ตกลางคันขณะส่ง → ต้องไม่เหลือ `case` ที่ไม่มี `transfer_leg`
- [ ] กดปุ่มส่งรัวๆ → ไม่เกิดเคสซ้ำ
- [ ] ไม่มีช่องกรอกเวลาด้วยมือในหน้านี้ (ยกเว้น `symptom_onset_at` ซึ่งเป็นเวลาในอดีตที่ผู้ใช้ทราบ)

### B4 — F2 หน้าศูนย์สั่งการ

- [ ] เคส `urgent` ขึ้นบนสุดเสมอ แม้สร้างทีหลัง
- [ ] เวลาที่รออยู่นับขึ้นเองโดยไม่ต้อง refresh
- [ ] จัดรถแล้ว `transfer_leg.status = 'dispatched'` และ `dispatched_at` ขึ้นเอง
- [ ] รถที่ถูกจัดแล้วเปลี่ยนสถานะเป็นไม่ว่าง
- [ ] **ทดสอบ realtime** — เปิด 2 browser แล้วสร้างคำขอในจอ A → จอ B เห็นภายใน 5 วินาที
- [ ] ตัดเน็ตของจอ B แล้วต่อกลับ → reconnect และข้อมูลตรงกัน

### B5 — F3 หน้าติดตามสถานะ

- [ ] timeline แสดงครบ 6 timestamp ของแต่ละทอด
- [ ] ปุ่มเปลี่ยนสถานะแสดงเฉพาะสถานะถัดไปที่เป็นไปได้
- [ ] **ข้ามขั้นไม่ได้** — พยายาม update จาก `pending` ไป `completed` ตรงๆ ผ่าน API → ถูกปฏิเสธ
- [ ] `assessment` ของทอดที่ 1 เปิดดูได้จากทอดที่ 2 และ 3 **โดยไม่ต้องคัดลอกข้อมูล** ← ข้อนี้คือหัวใจของโครงการ
- [ ] ทุกค่าประเมินมี timestamp กำกับ และระบุว่าเป็นผลจากทอดก่อนหน้า
- [ ] กด "ส่งทอดถัดไป" → เกิด `transfer_leg` ใหม่ `leg_no = 2` ภายใต้ `case` เดิม
- [ ] ทอดสุดท้าย `completed` → `case.status = 'completed'` และ `closed_at` ขึ้นเอง

### B6 — F4 แดชบอร์ด

- [ ] ตัวเลข response time **ไม่มีค่าติดลบ** (ถ้ามีแปลว่า constraint หรือ trigger พัง)
- [ ] จำนวนเคสบนแดชบอร์ดตรงกับ `select count(*) from "case"` ที่ผู้ใช้คนนั้นเห็นได้
- [ ] เปลี่ยนตัวกรองวันที่ → ตัวเลขเปลี่ยนตาม
- [ ] ไม่มีข้อมูล → แสดง empty state ที่บอกว่ายังไม่มีข้อมูล ไม่ใช่เลข 0
- [ ] ใช้ median ไม่ใช่ mean (ตรวจในโค้ด)
- [ ] ผู้ใช้ต่างหน่วยเห็นตัวเลขต่างกัน (RLS ทำงานผ่าน view ด้วย)

### B7 — F7 Export

- [ ] ไฟล์ CSV มีคอลัมน์ครบตาม spec รายงานสรุปกำลังพลบาดเจ็บ
- [ ] เปิดใน Excel แล้วภาษาไทยไม่เพี้ยน (UTF-8 with BOM)
- [ ] export ได้เฉพาะเคสที่ผู้ใช้มีสิทธิ์เห็น — ทดสอบด้วยผู้ใช้ 2 หน่วยแล้วเทียบจำนวนแถว

### B8 — Mobile และ Accessibility

- [ ] ทดสอบบนมือถือจริง ไม่ใช่แค่ย่อ browser
- [ ] ที่ความกว้าง 375px ไม่มี horizontal scroll
- [ ] ปุ่มหลักสูงอย่างน้อย 48px
- [ ] กรอกฟอร์มขอส่งกลับได้ด้วยนิ้วโป้งมือเดียว
- [ ] เปิดกลางแดด (หรือปรับ brightness สูงสุด) แล้วอ่านออก
- [ ] เปิด grayscale filter แล้วยังแยก triage color ได้ (ต้องมีตัวอักษรกำกับ)
- [ ] เนื้อหาผ่าน contrast WCAG AA
- [ ] 3G throttling → หน้าแรกโหลดได้ภายใน 5 วินาที

### B9 — Error handling

- [ ] ตัดเน็ตแล้วกดส่งฟอร์ม → ขึ้นข้อความที่เข้าใจได้ ไม่ใช่ error ดิบ
- [ ] Supabase ล่ม (ใส่ URL ผิด) → หน้าไม่ขาว แสดงข้อความบอกผู้ใช้
- [ ] เปิด `/track/<uuid ที่ไม่มีจริง>` → ขึ้น 404 ที่เข้าใจได้
- [ ] error message ไม่เปิดเผยชื่อตาราง คอลัมน์ หรือ stack trace ให้ผู้ใช้ทั่วไป

### B10 — Deployment

- [ ] Live URL เปิดได้จากมือถือ **นอกเครือข่ายหน่วย** (ใช้ 4G ไม่ใช่ WiFi ที่ทำงาน)
- [ ] Environment variable บน Vercel ครบและถูกต้อง
- [ ] Supabase redirect URL ตรงกับ production domain
- [ ] HTTPS ทำงาน
- [ ] Preview URL ของ branch ทำงานแยกจาก production

## C. UAT — ทดสอบกับผู้ใช้จริง

### กติกาก่อนเริ่ม

- **เป็นการขอความร่วมมือโดยสมัครใจนอกเวลา ไม่ใช่การสั่งการ** — บอกให้ชัดตั้งแต่ต้นและบันทึกไว้
- ใช้ **ข้อมูลจำลองเท่านั้น** ห้ามใช้เคสจริงของผู้ป่วยรายใด
- ผู้ทดสอบไม่ต้องมีความรู้ทางเทคนิค

### ผู้ทดสอบเป้าหมาย (3–5 คน)

| # | บทบาท | ทดสอบอะไร |
|---|---|---|
| 1 | เสนารักษ์ / นายสิบพยาบาล | F1 หน้าขอส่งกลับ |
| 2 | พลเปล / พลขับ | F3 การเปลี่ยนสถานะบนรถ |
| 3 | พยาบาลที่รับส่งต่อจริง | F5 หน้ารับผู้ป่วยปลายทาง |
| 4 | เจ้าหน้าที่ศูนย์สั่งการ | F2 หน้าศูนย์สั่งการ |
| 5 | ผู้บังคับหน่วย (ถ้าได้) | F4 แดชบอร์ด |

### วิธีทดสอบ

**ห้ามสอนวิธีใช้ก่อน** ให้โจทย์แล้วดูว่าเขาทำได้เองหรือไม่ — จับเวลาและจดจุดที่เขาลังเล

| งาน | โจทย์ที่ให้ | เกณฑ์ผ่าน |
|---|---|---|
| T1 | "มีทหารบาดเจ็บที่จุดฝึก อาการ [X] ขอส่งกลับหน่อย" | ส่งคำขอสำเร็จภายใน **90 วินาที** โดยไม่ถามวิธีใช้ |
| T2 | "รับภารกิจนี้ แล้วบันทึกว่าถึงจุดรับแล้ว" | หาปุ่มเจอภายใน **20 วินาที** |
| T3 | "ดูหน่อยว่ามีใครกำลังจะมา อาการเป็นอย่างไร" | บอกอาการและ triage ได้ถูกต้องภายใน **30 วินาที** |
| T4 | "เดือนนี้ส่งกลับกี่เคส เร่งด่วนกี่เคส" | อ่านตัวเลขจากแดชบอร์ดได้ถูกต้อง |

### สิ่งที่ต้องจดระหว่างทดสอบ

- จุดที่ผู้ใช้**ลังเลเกิน 5 วินาที** ← สำคัญกว่าคำติชมด้วยวาจา
- คำที่ผู้ใช้ใช้เรียกสิ่งต่างๆ ถ้าไม่ตรงกับที่ระบบใช้ **ให้เปลี่ยนระบบตามผู้ใช้ ไม่ใช่สอนผู้ใช้**
- สิ่งที่ผู้ใช้พยายามทำแต่ระบบไม่มี
- จำนวนครั้งที่ต้องช่วย

### คำถามหลังทดสอบ

1. ถ้าต้องใช้จริงพรุ่งนี้ ใช้ได้เลยไหม ติดอะไรบ้าง
2. เทียบกับวิธีเดิม (วิทยุ/กระดาษ/LINE) อันไหนเร็วกว่า เพราะอะไร
3. มีอะไรที่ระบบทำแล้วคุณไม่อยากให้ทำ
4. ถ้าตัดฟีเจอร์ออกได้ 1 อย่าง จะตัดอะไร

### Baseline ที่ต้องเก็บควบคู่

> ⚠️ ปัจจุบัน**ยังไม่มีตัวเลข baseline ใดๆ** เพราะข้อมูลก่อนถึงโรงพยาบาลไม่เคยถูกเก็บอย่างเป็นระบบ

ระหว่าง UAT ให้เก็บ

- [ ] **จับเวลาการทำรายงานประจำวันด้วยวิธีเดิม** (นาที/วัน) → เทียบกับเวลาที่ใช้ export จากระบบ
- [ ] จำนวนครั้งที่ปลายทางต้องโทรถามข้อมูลซ้ำในสัปดาห์นั้น
- [ ] จำนวนเคสส่งกลับต่อสัปดาห์ตามปกติของ พัน.สร.4

**การไม่มี baseline คือหลักฐานของปัญหา ไม่ใช่จุดอ่อนของโครงการ** — พูดตรงๆ บนเวที

## D. Regression — รันซ้ำก่อนส่งงาน 13 ก.ย.

รายการนี้คือข้อที่ถ้าพังจะทำให้ demo ล่มบนเวที เรียงตามความเสี่ยงจากมากไปน้อย

1. [ ] **B1 ทั้งหมด** — RLS พังคือพังทั้งระบบ และเป็นข้อที่กรรมการจะถาม
2. [ ] **B5 ข้อ assessment ข้ามทอด** — เป็น HMW หลักของโครงการ ถ้าข้อนี้ demo ไม่ได้ เรื่องเล่าทั้งหมดพัง
3. [ ] **B10 Live URL จากมือถือนอกเครือข่าย** — เวทีอาจไม่มี WiFi ที่ทำงาน
4. [ ] **B4 realtime** — ถ้าไม่ทำงาน ต้องเตรียมบอกล่วงหน้าว่าจะกด refresh
5. [ ] **B6 ตัวเลขไม่ติดลบ** — ตัวเลขประหลาดบนจอทำลายความน่าเชื่อถือทันที
6. [ ] **B3 transaction** — เคสค้างครึ่งๆ ระหว่าง demo คือหายนะ
7. [ ] **B8 mobile** — demo จะทำบนมือถือ
8. [ ] seed data มีเคสค้างที่สถานะ `dispatched` ไว้ 1 เคส สำหรับ demo สด

### แผนสำรองบนเวที

- [ ] อัดวิดีโอ demo ไว้ล่วงหน้า เผื่อเน็ตล่ม
- [ ] screenshot ทุกหน้าจอใส่สไลด์ไว้ เผื่อทั้งเน็ตและวิดีโอล่ม
- [ ] เตรียมมือถือ 2 เครื่อง (ตัวเองและสำรอง) พร้อม hotspot ของตัวเอง
- [ ] login ค้างไว้ทั้ง 2 เครื่องก่อนขึ้นเวที
